# Cocos Creator 项目优化审计

## 工作目标

把项目读成一份可执行的优化报告：先用数据定位高收益问题，再结合 Cocos Creator 的资源加载、Asset Bundle、场景、Prefab、脚本和构建配置给出开发者能直接落地的改法。不要只给泛泛建议；每条建议都要说明证据、影响、修复步骤和验证方式。

## 快速流程

1. 确认项目根目录：优先查找 `assets/`、`project.json`、`settings/`、`extensions/`、`packages/`、`build/`、`native/engine/`。
2. 运行脚本获取资源画像：

```bash
python <skill-dir>/scripts/audit_cocoscreator_project.py <project-root> --output cocos-audit.md
```

3. 阅读脚本报告中排名靠前的目录、扩展名、大文件、重复文件、疑似未引用资源、复杂场景和复杂 Prefab。
4. 补充人工阅读：抽查关键场景、资源加载代码、bundle 配置、常驻节点、对象池、纹理压缩、音频格式、动态图集和构建设置。
5. 输出优化报告，按收益和风险排序，不要把所有发现平铺成同等优先级。

## 必查维度

### 资源体积

- 统计 `assets/`、`resources/`、各 bundle、`build/` 输出目录的体积占比。
- 优先关注图片、音频、Spine/DragonBones、视频、字体、JSON、二进制大表。
- 对图片检查：分辨率是否超过显示需求，是否有透明通道浪费，是否未使用纹理压缩，是否适合拆分或合图。
- 对音频检查：BGM 与音效格式是否区分，长音频是否压缩，重复音效是否复用，是否有无用多语言资源。
- 对 `resources/` 特别谨慎：这里的资源容易被整体打包，建议迁移到明确的 Asset Bundle 或按需加载目录。

### 重复与疑似未引用资源

- 用哈希识别完全重复文件，合并前先确认 `.meta`、Prefab/Scene 引用、平台差异和美术命名约定。
- 对同名、同尺寸但哈希不同的资源，标为“疑似重复”，需要人工比对。
- 通过 `.meta` 的 `uuid` 在项目文本中搜索引用，找出疑似未引用资源；不要直接删除，先让开发者在编辑器中确认依赖和动态加载路径。
- 特别检查历史活动、废弃皮肤、测试目录、临时导出目录、设计稿源文件是否进入包体。

### 场景、Prefab 与节点层级

- 找出体积大、节点多、组件多、嵌套深的 `.scene`、`.fire`、`.prefab`。
- 检查常驻场景是否塞入过多 UI、特效、音频和业务对象。
- 检查频繁创建销毁的节点是否适合对象池，列表/背包/弹窗是否复用 item。
- 对复杂 Prefab 建议拆分为懒加载子模块，避免首屏或切场景一次性加载过多依赖。

### 加载、释放与内存管理

- 搜索 `resources.load`、`resources.loadDir`、`assetManager.loadBundle`、`bundle.load`、`instantiate`、`destroy`、`release`、`decRef`、`addRef`、`NodePool`。
- 对动态加载资源，确认生命周期：谁加载、谁持有、何时释放、是否被全局缓存或事件监听阻止释放。
- 对常用资源区分“常驻缓存”和“短生命周期资源”，不要盲目释放会反复使用的小资源。
- 检查事件监听、定时器、Promise/回调、单例缓存是否在节点销毁后仍持有对象。

### 包体、首屏与运行时性能

- 检查首包资源是否只包含启动必需内容，非首屏玩法、活动、皮肤、语音、视频应拆 bundle 或远程包。
- 检查动态图集、静态合图、Label 字体、Spine 骨骼数量、粒子数量、材质数量和 draw call 风险。
- 结合目标平台区分建议：微信小游戏、Web、Android、iOS、原生平台的包体限制和压缩策略不同。

## 判断原则

- 不要建议直接删除脚本列出的“未引用资源”；只能标记为候选，因为动态字符串加载和远程配置可能绕过静态扫描。
- 不要为了“整洁”建议大范围重构。优先提出小步、可验证、高收益的优化。
- 每个建议都要能被开发者执行：给出文件、目录、资源类型或代码模式。
- 如果证据不足，明确写“需要确认”，不要假装确定。
- 修改建议要兼顾 Cocos Creator 版本差异；不确定版本时，先说明按 2.x/3.x 通用思路处理。
