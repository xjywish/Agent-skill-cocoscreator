# Cocos Creator 游戏项目优化审计

## 角色定位

把自己当成接手项目上线前优化的资深游戏客户端开发者，而不是只做文件统计的脚本。审计时始终围绕四个问题判断价值：

- 玩家是否更快进入游戏：首包、首屏、登录链路、切场景耗时。
- 运行时是否更稳：内存峰值、释放策略、对象池、事件监听、低端机风险。
- 包体是否更轻：资源压缩、重复资源、废弃资源、Bundle 划分、平台差异。
- 团队是否能落地：每条建议都要给证据、改法、验证方式和风险。

不要只输出“发现了哪些文件”。要把发现转成开发者能执行的优化任务。

## 快速用法

优先输出 HTML，方便团队阅读和评审：

```bash
python <skill-dir>/scripts/audit_cocoscreator_project.py <project-root> --output cocos-audit.html
```

如需纯文本版本：

```bash
python <skill-dir>/scripts/audit_cocoscreator_project.py <project-root> --format md --output cocos-audit.md
```

如果用户只要求“审计项目”，先运行脚本拿数据画像，再人工阅读关键目录和代码，最后输出完整报告。脚本报告是证据底稿，不是最终结论。

## 审计流程

1. 确认项目上下文：Cocos Creator 版本、目标平台、首包限制、是否小游戏、是否热更新、是否使用远程 Bundle。
2. 跑脚本生成资源画像：总体积、目录体积、扩展名体积、大文件、重复文件、疑似未引用资源、复杂 Scene/Prefab。
3. 从游戏运行链路审计：启动场景、登录/大厅、核心玩法场景、常驻节点、弹窗系统、列表系统、特效和音频管理。
4. 从资源生命周期审计：加载入口、缓存策略、释放责任、跨场景引用、全局单例、事件监听、对象池。
5. 输出按优先级分层的报告：P0 立刻处理、P1 近期优化、P2 后续治理、需要人工确认。

## 必查维度

### 1. 包体与首屏

- 检查首包是否只包含启动必需资源；非首屏玩法、活动、皮肤、语音、视频应拆到 Bundle 或远程包。
- 特别关注 `assets/resources/`：这里的资源常被整体纳入包体或形成隐性依赖，优先建议迁移到明确 Bundle。
- 检查构建输出、小游戏分包、热更新目录和平台差异资源，避免测试资源、源文件、历史活动混入包体。

### 2. 资源大小与压缩策略

- 图片：分辨率是否超过显示尺寸，透明通道是否浪费，是否开启平台纹理压缩，UI 图和大背景是否适合合图/拆分。
- 音频：BGM 与音效格式是否区分，长音频是否压缩，短音效是否复用，采样率是否过高。
- Spine/DragonBones/粒子：骨骼数、贴图尺寸、动画数量、特效生命周期是否适合目标机型。
- 字体/多语言/配置：是否把未使用语言包、设计源文件、大 JSON 表直接打进首包。

### 3. 重复与疑似未引用资源

- 用哈希确认完全重复文件；合并前检查 `.meta`、Prefab/Scene 引用、平台差异和美术命名约定。
- 对同名、同尺寸、同类型但哈希不同的资源，标记为“疑似重复”，需要人工比对。
- 通过 `.meta` 的 `uuid` 静态搜索疑似未引用资源；只能列为候选，不要直接删除，因为动态字符串加载和远程配置会造成误报。

### 4. 场景、Prefab 与节点层级

- 找出体积大、依赖多、节点多、组件多、嵌套深的 `.scene`、`.fire`、`.prefab`。
- 检查常驻场景是否塞入过多 UI、特效、音频、业务对象。
- 检查列表、背包、排行榜、弹窗、飞字、特效是否频繁 instantiate/destroy，是否需要对象池。
- 对复杂 Prefab 建议拆成懒加载子模块，避免首屏或切场景一次性加载过多依赖。

### 5. 加载释放与内存管理

- 搜索 `resources.load`、`resources.loadDir`、`assetManager.loadBundle`、`bundle.load`、`instantiate`、`destroy`、`release`、`decRef`、`addRef`、`NodePool`。
- 对动态资源明确生命周期：谁加载、谁持有、何时释放、是否被全局缓存、事件监听、定时器、Promise/回调继续持有。
- 区分常驻缓存和短生命周期资源；不要盲目释放高频复用的小资源，也不要让活动资源常驻。

### 6. 渲染与运行时性能

- 检查 DrawCall 风险：动态图集、静态合图、材质数量、字体 Label、Spine、粒子、遮罩和混合模式。
- 检查低端机压力：同屏节点数、动画数、粒子数、骨骼动画数、频繁布局刷新、列表 item 回收。
- 对性能建议要绑定场景：启动、登录、大厅、战斗、活动页、背包、排行榜等。

## 判断原则

- 先高收益、低风险；后结构治理。不要为了“优雅”建议大范围重构。
- 每条建议都要能追溯到证据：文件、目录、资源类型、代码模式或运行链路。
- 不确定时写“需要确认”，不要把静态扫描结果当成事实。
- 删除资源必须保守：先列候选、再让开发者用编辑器依赖、运行日志和灰度包验证。
- 版本差异要明确：不确定 Cocos Creator 版本时，按 2.x/3.x 通用思路处理。
